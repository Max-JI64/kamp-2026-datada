# jsw EDA 작업 규칙

이 문서는 `EDA/jsw`에서 진행하는 개인 EDA의 공통 기준이다. 분석 코드 작성과 실행, 결과 해석, 문서 정리 시 아래 규칙을 따른다.

## 1. 작업 범위와 원본 보존

- 분석 코드, 결과표, 플롯, 분석 문서, 로그는 모두 `EDA/jsw` 아래에 작성한다.
- 다른 팀원의 EDA 폴더와 프로젝트 공용 파일은 임의로 수정하지 않는다.
- `data/origin`은 원본 전용이다. 읽기만 하며 수정, 덮어쓰기, 삭제하거나 분석 산출물을 저장하지 않는다.
- 전처리 데이터와 파생변수가 포함된 데이터는 예외적으로 프로젝트의 `data/processed` 아래에 저장한다. 팀원 산출물과 구분하기 위해 `data/processed/jsw`를 사용한다.
- 단순 요약·집계 결과표는 `EDA/jsw/tables`에 저장한다. 행 단위 가공 데이터는 `data/processed/jsw`에 저장한다.
- 이번 규칙 문서 작성 이후 실제 분석은 사용자가 요청한 범위에서 진행한다.

## 2. 상대경로 사용

- 데이터 입력·출력 경로는 반드시 상대경로로 작성한다. 개인 PC의 드라이브명이나 절대경로를 코드·설정에 넣지 않는다.
- 기본 실행 위치는 `EDA/jsw`로 통일한다. 실행 명령과 실행 위치를 로그에 함께 기록한다.
- 코드는 `scripts` 아래에 두며, 경로는 다음처럼 스크립트 위치를 기준으로 구성해 실행 위치 차이로 인한 오류를 줄인다.

```python
from pathlib import Path

EDA_DIR = Path(__file__).parent.parent
ORIGIN_DIR = EDA_DIR / "../../data/origin"
PROCESSED_DIR = EDA_DIR / "../../data/processed/jsw"
TABLE_DIR = EDA_DIR / "tables"
FIGURE_DIR = EDA_DIR / "figures"
```

- 예시 데이터 경로: `../../data/origin/<원본 파일명>`.
- 파일을 찾지 못하면 경로와 실행 위치부터 확인한다. 원본을 작업 폴더에 복사해서 해결하지 않는다.

## 3. Python 분석 → 결과 확인 → 문서 작성

1. 분석 질문과 확인할 항목을 간단히 정한다.
2. Python `.py` 스크립트로 분석한다. `.ipynb`는 사용하지 않는다.
3. 결과표와 플롯을 파일로 저장한다. 콘솔 출력만 남기지 않는다.
4. GPT는 저장된 결과표의 수치와 생성된 플롯을 실제로 확인한 뒤 해석한다. 확인하지 못한 결과는 미확인으로 표시한다.
5. 팀원이 읽을 수 있는 Markdown 분석 문서로 정리하고, 근거가 되는 결과 파일을 상대 링크로 연결한다.
6. 분석 과정과 결과, 후속 작업을 `LOG.md`에 기록한다.

- 최초 데이터 확인은 파일 구성, 컬럼, 자료형, 행 수, 제한된 샘플부터 시작한다. 필요 없이 전체 데이터를 출력하지 않는다.
- 표에는 단위, 집계 기준, 표본 수와 결측치 처리 기준을 적는다. 비율에는 분모를 명시한다.
- 플롯에는 제목, 축 이름, 단위를 표시한다. 필요한 경우 범례와 분석 대상을 덧붙인다.
- CSV는 특별한 사유가 없으면 `utf-8-sig`, Markdown·소스 파일은 UTF-8을 사용한다. 다른 인코딩이 확인되면 그 근거를 기록한다.

## 4. 분석 깊이와 해석 기준

- 팀원이 이해하고 다음 분석에 활용할 수 있는 수준을 우선한다.
- 하나의 질문에 필요한 기본 통계와 플롯부터 확인한다. 목적 없이 기법이나 파생변수를 늘리지 않는다.
- 전문 용어와 변수명은 처음 등장할 때 의미를 설명한다. 개인만 아는 약어와 생략된 전제를 사용하지 않는다.
- 관찰된 사실, 가능한 해석, 추가 확인이 필요한 가설을 구분한다.
- 상관관계를 인과관계로 단정하거나, 일부 표본의 결과를 전체 공정에 일반화하지 않는다.
- 데이터에 없는 공정 지식, 변수의 의미, 이상치 발생 원인을 만들어내지 않는다. 불명확하면 `확인 필요`로 남긴다.
- 분석 질문에 답을 얻으면 핵심 결과와 한계를 정리한다. 더 깊은 분석은 필요한 이유를 먼저 적고 진행한다.

## 5. 전처리와 파생변수

- 결측치 처리, 이상치 제거, 자료형 변환, 중복 제거, 파생변수 생성은 이유와 적용 기준을 기록한다.
- 가공 데이터마다 입력 파일, 사용 코드, 처리 내용, 처리 전후 행·열 수, 저장 위치를 남긴다.
- 파생변수는 변수명, 의미, 계산식, 단위를 기록한다.
- 가공 결과는 원본부터 코드로 다시 만들 수 있어야 한다. 수동 편집으로만 존재하는 데이터는 만들지 않는다.
- 기존 가공 파일을 조용히 덮어쓰지 않는다. 변경된 기준으로 만들면 새 작업 번호를 부여하고 이전 결과와의 관계를 기록한다.

## 6. 파일명과 작업 순서

- 모든 분석 코드명은 `MM.DD_번호_작업내용.py` 형식을 사용한다.
- 날짜는 해당 작업을 시작한 날짜이며, 번호는 `001`부터 전체 작업에 걸쳐 순서대로 증가한다. 날짜가 바뀌어도 초기화하지 않는다.
- 예: `09.22_001_data_overview.py`, `09.22_002_missing_values.py`, `09.23_003_distribution.py`.
- 같은 분석의 결과표·플롯·문서는 코드와 같은 날짜·번호를 사용한다. 결과가 여러 개라면 설명을 뒤에 붙인다.
- 예: `09.22_001_column_summary.csv`, `09.22_001_missing_ratio.png`, `09.22_001_data_overview.md`.
- 단순 오류 수정과 재실행은 같은 번호를 유지하고 변경 내용을 로그에 추가한다. 분석 목적이나 처리 기준이 바뀌면 새 번호를 사용한다.
- `AGENTS.md`와 `LOG.md`처럼 계속 유지하는 관리 문서는 날짜·번호 규칙의 예외다.
- 파일명에 연도가 없으므로 실제 연도와 실행 시각은 로그에 반드시 남긴다.

## 7. 폴더 구성

아래 폴더는 실제 산출물이 필요할 때 생성한다.

```text
EDA/jsw/
├── AGENTS.md       # 이 작업 규칙
├── LOG.md          # 시간순 작업 기록
├── scripts/        # Python 분석 코드
├── tables/         # 요약·집계 결과표
├── figures/        # 플롯
└── reports/        # 결과를 해석한 Markdown 문서

data/processed/jsw/ # 전처리·파생변수 데이터
```

## 8. 분석 문서 구성

각 문서는 다음 순서로 간결하게 작성한다.

1. **분석 목적**: 무엇을 확인하려는가.
2. **데이터와 방법**: 입력 파일, 분석 범위, 표본 수, 집계·처리 기준.
3. **주요 결과**: 실제 수치와 결과표·플롯 링크.
4. **해석과 한계**: 확인된 사실, 가능한 해석, 확인하지 못한 사항.
5. **다음 작업**: 필요한 경우에만 후속 질문을 적는다.
6. **재현 정보**: 사용 코드, 실행 위치·명령, 관련 작업 번호.

## 9. LOG 기록 기준

- `LOG.md`에는 작업을 오래된 순서부터 아래로 추가한다. 과거 기록을 지워 진행 이력이 사라지게 하지 않는다.
- 분석 시작·완료, 실패, 재실행, 기준 변경을 기록한다. 실패를 완료로 표시하지 않는다.
- 시각은 한국 시간 기준 `YYYY-MM-DDTHH:mm+09:00` 형식으로 작성한다.
- 아래 항목으로 나중에 분석 순서와 판단 근거를 재구성할 수 있게 한다.

```markdown
### YYYY-MM-DDTHH:mm+09:00 | MM.DD_번호 | 작업명 | 시작/완료/실패/재실행

- 목적:
- 입력 파일 및 범위:
- 실행 위치와 명령:
- 수행 내용 및 변경 이유:
- 산출물 경로:
- 확인한 결과: 핵심 수치, 검증 내용, 종료 코드 등
- 한계·오류·미확인 사항:
- 다음 작업:
```

- 난수를 쓰면 시드를 기록하고, 결과에 영향을 주는 주요 옵션과 패키지 버전도 남긴다.
- 실행하지 않은 코드는 `미실행`, 열어보지 않은 표·플롯은 `미확인`이라고 적는다.
